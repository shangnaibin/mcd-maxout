# 麦尽其用 · MaxOut

> 别问「100 块能吃什么」，问「100 块能吃几个」——给定预算，把一种餐品买到数学上的最多。

**[👉 在线试用：https://shangnaibin.github.io/mcd-maxout/](https://shangnaibin.github.io/mcd-maxout/)**

不用装、不用配 token，点开输入预算和想囤的餐品，立刻算出最多能买几个、怎么组合。
页面里是同构的纯前端求解器，数据是某门店的真实菜单快照（含券与会员价）。

给定一个预算和一种想囤的餐品，**算出最多能买几个、怎么组合、剩下几块钱还能塞点什么**。
答案不是估的：菜单来自麦当劳 MCP `query-meals`，套餐结构来自 `query-meal-detail`，
最终总价用官方 `calculate-price` 复核。

```
门店：麦当劳天津峰汇华夏未来餐厅
预算 ¥100.00　目标：最多能买几个双层吉士汉堡
────────────────────────────────────────────
最优方案：最多 6 个双层吉士汉堡
  ×6  人气经典随心配（双层吉士汉堡/小杯玉米杯）  @¥14.90  小计 ¥89.40
  ×2  灰焰圆筒                                  @¥5.00   小计 ¥10.00
  实付 ¥99.40 / 预算 ¥100.00，余额 ¥0.60
  顺带还有 8 件其他餐品（原价合计 ¥88.00）
────────────────────────────────────────────
对照：只单买双层吉士汉堡，4 个，花 ¥92.00
      ↑ 用对组合，同样预算多拿 2 个
官方核价：¥99.40　一致 ✅
```

## 它解决的问题

市面上的点餐助手都在回答「这一单怎么点最省」。但真实场景里还有另一类问题：

- 部门团建，100 块能买几个汉堡，尽量人手一个？
- 宿舍夜宵，50 块最多能搞几个麦香鸡？
- 就想囤一堆双层吉士，怎么买最划算？

这类问题本质是**整数规划**：预算固定、每种购买单位可重复、目标是某一商品件数最大。
靠大模型心算必然出错，靠贪心会错过组合。麦尽其用把它交给确定性算法。

## 为什么能算出别人算不出的答案

麦当劳的价格结构有三层，只看标价会漏掉最便宜的那条路：

1. **单品价**：双层吉士汉堡 ¥23.00
2. **套餐价**：板烧鸡腿堡三件套 ¥34.50（堡 + 薯条 + 可乐）
3. **随心配**：¥14.90，蓝区选一个汉堡 + 粉区选一个饮料/小食，**不同选法还要加减差价**
   （选麦香鸡 −¥1.00 → ¥13.90；选双层吉士 ±¥0 → ¥14.90）

同一个双层吉士，单买 23.00，走随心配只要 14.90，**单位成本直接降到 65%**。
100 块从 4 个变成 6 个，靠的就是这一层。

4. **优惠券 / 活动**：券是绑在**具体商品行**上的（`couponCode` + `couponId`），
   一张券把某个商品的价格直接压到券面价。60 块的麦旋风，用 1 张「买一送一」
   能从 4 个变成 5 个；**能用 3 次（比如每天领一张）就是 7 个**——能用几次是
   一个独立参数 `uses`，它和「分开下单」是两回事，见下节。

麦尽其用会把每个套餐、每个随心配**按轮次展开成所有可选组合**（一次运行会生成
上万个候选购买单元），把券和活动折算成**有次数上限的购买单元**，再在预算内做精确求解。

## 优惠券怎么参与计算

券不是「最后减几块」，它改变的是某一行商品的单价，所以必须进到求解过程里。

**先澄清一个直觉误区：「分开下单」本身不会更便宜。** 券绑在商品行上，
同一笔订单里多行各带一张券在接口层面就成立——真正卡住数量的不是「下几单」，
而是「你手里有几张同款券」。所以模型里的关键参数是 `uses`：

- `uses=1`（默认）：只有一张真券（券码唯一，物理上只能核销一次）
- `uses=n`：能拿到 n 张同款券，或活动可参与 n 次
- `uses=0` / `"unlimited"`：不限次（只有纯活动规则才该这么写）

`uses>1` 在数学上是**有界背包**：每张券最多用 n 次。解法是把 n 次按二进制
分解成 1+2+4+… 个 0/1 块，继续用「券子集 × 无限背包」的组合，仍然全局最优：

```
最优解 = max over 券的子集 S ( 券的收益(S) + 无券无限背包(预算 − 券花费(S)) )
```

- 无券部分：标准无限背包，动态规划精确求解
- 券部分：券的数量很少（通常 < 10 张），枚举 2^k 个子集即可
- 两部分可加是因为无券单元之间可以任意替换，顺序无关

如果真要拆成多单（比如平台限制每单一张券）：**到店自取拆单没有额外成本，
外送拆单每单都会多付配送费**，方案输出里会按券的张数提示需要拆几单。

一个测试钉出来的真 bug：二进制分解会把「用 4 次」拆成 1+2+1 两个同内容块，
如果按内容去重就会丢块、把次数算少——自测（`python -m tests.test_optimality`）
用暴力枚举对比抓到了它，现在只有真实券码才去重。

券的情况分三种，输出里会明确标注：

| 标记 | 含义 | 能否官方核价 |
|---|---|---|
| `[券]` | 接口返回了真实 `couponCode` / `couponId` | ✅ 会带券码逐行核价 |
| `[预演]` | 券名能解析、但没领到券（没有券码） | ❌ 只作上限参考 |
| `[预演?]` | 券名与菜单名只能模糊匹配，需人工确认 | ❌ 只作上限参考 |

```
优惠券池：5 张可用
来源：可领券预演（未领到、无券码，仅供上限参考）
  [预演] 19.9元王牌炸鸡任选2 → 蘸酱炸鸡×2　单点 ¥23.80 → 用券 ¥19.90（省 ¥3.90）
  [预演?] 11.9元麦辣鸡腿堡 → 麦辣鸡腿汉堡×1　单点 ¥22.50 → 用券 ¥11.90（省 ¥10.60）
  [预演] 人气麦旋风买一送一 → 经典麦旋风×2　单点 ¥30.00 → 用券 ¥15.00（省 ¥15.00）
────────────────────────────────────────────
最优方案：最多 5 个经典麦旋风
 券 ×1  人气麦旋风买一送一｜经典麦旋风×2  @¥15.00  小计 ¥15.00
 券 ×1  免费脆薯饼                      @¥0.00   小计 ¥0.00
    ×3  经典麦旋风                       @¥15.00  小计 ¥45.00
  实付 ¥60.00 / 预算 ¥60.00，余额 ¥0.00
  其中优惠券抵扣 ¥30.50（2 张）
────────────────────────────────────────────
对照②：不用券、只算套餐 → 4 个，实付 ¥60.00
      ↑ 用对组合，同样预算多拿 1 个
```

活动也一样能算：`coupons.example.json` 支持 `fixed`（固定价）、`free`（免费）、
`bogo`（买一送一）、`half_second`（第二份半价）四种形式。
带 `couponCode` 的走核价链路，不带的当活动规则用。

每条规则都能加 `"uses"`：这套优惠能用几次（`1` 默认 / `3` 三次 / `0` 或
`"unlimited"` 不限次）。填了真实券码时 `uses` 恒为 1——一个券码物理上只能核销一次；
想表达「有三张同款券」，写三条各带自己券码的规则就好。


## 目标函数（字典序，逐级比较）

1. 目标餐品**份数最多**
2. 顺带买到的其他餐品**件数最多**（同价别浪费）
3. 顺带餐品的**原价合计最大**（同样花钱，尽量多拿东西）
4. **花得更少**（余钱更多）

## 使用示例

```bash
# 先看这家店有哪些汉堡，拿到编码和价格
python -m maxout --store 1980241 --list

# 懒人模式：给城市和地标，自己找最近的门店
python -m maxout --city 天津 --keyword 华盛广场 --budget 100 --target-name 麦香鸡

# 只要 7 个麦香鸡、再顺带 7 杯玉米杯，官方核价确认
python -m maxout --store 1980241 --budget 100 --target-name 麦香鸡 --verify

# 只看单品、不拆套餐（用来对比「套餐到底省了多少」）
python -m maxout --store 1980241 --budget 100 --target-name 板烧 --no-combos

# 机器可读，方便接自己的前端
python -m maxout --store 1980241 --budget 100 --target-name 巨无霸 --json

# 券：默认 auto（先查真实券，没有就用可领券做上限预演）
python -m maxout --store 1980241 --budget 60 --target-name 麦旋风

# 只认真实券，宁可不省也不用预演
python -m maxout --store 1980241 --budget 100 --target-name 双层吉士 --coupons wallet

# 用本地规则文件描述没有券码的活动（买一送一 / 第二份半价）
python -m maxout --store 1980241 --budget 60 --target-name 麦旋风 \
  --coupons file --coupon-file coupons.example.json

# 生成一张可以发群里的报告页（单文件 HTML，双击就能开，截图友好）
python -m maxout --store 1980241 --budget 100 --target-name 双层吉士 --verify --html
python -m maxout --store 1980241 --budget 100 --target-name 双层吉士 --html out/分享.html
```

### 参数

| 参数 | 说明 |
|---|---|
| `--store` | 门店编码，直接从 `--list` 的输出里取 |
| `--city` `--keyword` | 不指定门店时，按城市 + 地标搜索最近门店 |
| `--budget` | 预算（元），默认 100 |
| `--target-name` | 想囤的商品名关键词，例如 `双层吉士`、`麦香鸡`、`巨无霸` |
| `--target` | 商品编码，精确指定 |
| `--no-combos` | 只考虑单品 |
| `--cards` | `auto`（默认，比较开卡 vs 不开卡）/ `off`（只按原价算） |
| `--card-price` | 开卡费（元），默认 19。**接口不返回卡费**，按麦当劳 App 实际页价填 |
| `--card-uses` | 会员价一个周期可用几次，默认 2（官方权益页：超值四件套每日最高共 2 次） |
| `--coupons` | `auto`（默认）/ `wallet` / `preview` / `file` / `off` |
| `--coupon-file` | 本地券 / 活动规则 JSON，格式见 `coupons.example.json` |
| `--verify` | 调官方 `calculate-price` 复核总价（含券码时逐行核） |
| `--html [路径]` | 生成可分享的单文件 HTML 报告，缺省写到 `out/` |
| `--json` | 输出 JSON |

## 报告页：一张截图讲完整个方案

`--html` 会生成一份单文件报告（内联样式、零外部依赖），包含：

- **组合明细**：每个单元带「券 / 套餐 / 单品」标签，单价、小计

## 自测：最优性是证明出来的，不是声称的

```bash
python -m tests.test_optimality
# 全部通过：券子集 × 背包的最优解与暴力枚举一致（含会员卡次数额度）
```

离线跑 40 组随机用例（随机预算 + 随机券）+ 30 组多次券用例 + 30 组会员卡用例，
每一组都拿暴力枚举当基准对答案。
这个测试专门盯住两类陷阱：**贪心用券是错的**——
「这张券面额大」不等于「用了它就能多买一个」，
占用预算反而会少买一件目标商品；**会员价当无限用是错的**——
额度上限直接决定「开卡划不划算」的结论。只有精确枚举/分层 DP 才能不漏最优。


## 一个会让所有工具算错钱的坑

菜单里有一批商品的 `currentPrice` **不是裸价**，而是「随单购麦金卡」的专属价。
例如某店的「鱼牛汉堡四件套随心选」标价 ¥32.00，但那是要同时买卡才成立的价格，
不加 `withOrder` 直接下单，官方计价接口返回的是 **¥59.50**，差 86%。

如果不识别这一点，任何「按菜单价算最省」的工具都会给出虚高的结论。
麦尽其用的做法是：**把这类商品展开成两套购买单元**——
原价单元（`originalPrice`，不开卡时的真实价）和会员价单元（菜单标价，走开卡分支），
两套都参与求解，「开卡到底划不划算」从此有对照组，而不是靠拍脑袋。

`--verify` 就是为了兜住这类坑：本地算 60.00、官方算出 87.50 的那次，就是它先喊出来的。

## 开会员（麦金卡）到底会不会多买几个

这是会员价单元的直接应用。模型把「开卡」变成一个**有成本、有次数额度**的分支：

- **卡费**：接口不返回，`--card-price` 手填（默认 19 元/30 天，来自公开资料，页面可改）
- **次数额度**：官方权益页写明「超值四件套每日最高**共**可享 2 次，每次限一份」，
  所以会员价不是无限用，默认按共享额度 2 建模（`--card-uses` 可改）
- **求解**：分层 DP——第 k 层表示已用掉 k 次会员价额度，层内普通单元无限松弛，
  用一次会员价就跳到下一层；与券子集枚举组合后仍是全局最优（有暴力枚举对答案的测试）

实测结论（100 元囤板烧鸡腿堡）：开卡后卡费吃掉预算，会员价四件套 28 元
单个目标的成本并不比单买 23.5 元低，**份数反而从 4 个掉到 3 个**。
卡的价值在别处：一次开卡方案里会员价能省 59 元，远超 19 元卡费（一次下单就回本），
顺带餐品更多、还有满额免配送费——适合「吃得丰富」，不适合「囤得多」。
工具会把这两面都算给你看，包括回本线。

另一个实测事实：**未持卡账号调 `calculate-price` 传 `withOrder` 不生效**，
一律按原价返回。所以含会员价的方案会被核价环节如实标注「无法官方核价」，而不是假装核对过。

## 关于券的三个实测结论

1. **券是按商品行绑定的**，不是订单级满减。`calculate-price` 的 `items[].couponCode` /
   `couponId` 才是入口，满减券（「满 30 减 5」）目前没有对应字段，本项目会明确标注不支持，
   而不是假装算进去。
2. **假券码会被服务端拒绝**：随便传一个 `couponCode` 过去，接口直接返回
   「未找到优惠券或已赠送给好友」。所以核价环节天然能拦住「用错券」「券与商品不匹配」，
   不会算出一个人人都满意的假价格。
3. **券名和菜单名不一定一致**：券写「麦辣鸡腿堡」，这家店菜单写「麦辣鸡腿汉堡」；
   券写「脆薯饼」，菜单写「心形薯饼5块」。所以匹配分三级——精确、相似度、失败，
   相似度匹配会打上 `[预演?]` 标记，绝不悄悄当成确定答案。


## 目标用户

- **预算固定的组织者**：团建、班会、宿舍夜宵，要的是「人手一个汉堡」而不是「最便宜的一单」
- **有明确执念的人**：「我这周就想吃双层吉士」，只想把预算全部换成它
- **想知道套餐到底值不值的人**：`--no-combos` 一跑，套餐省了多少一目了然

## 设计取舍

- **确定性优先**：优化交给动态规划，大模型只负责把口语翻成参数。同一份菜单永远得到同一个答案，可复现、可测试。
- **不替用户下单**：本项目只做方案与核价，`create-order` 不在默认链路里，付款必须由用户本人确认。
- **数据不落盘**：Token 只从环境变量读，菜单数据只在内存里用，不写缓存、不收集任何个人信息。
